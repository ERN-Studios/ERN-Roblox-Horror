# Level 2 kit adversarial review (pre-Studio)

## 1. [major; verifiers: major,major; upheld 2/2] Manifest BuoyantProps = {} makes every Pool Slide spawn pass throw, so the Pool Slide never spawns
- `ServerScriptService/Level 2 Systems/Level 2 Kit World Builder.ModuleScript.lua:1331` (builder-contract)
- Detail: The builder returns `BuoyantProps={}`, an empty Lua table, which is truthy. Pool Slide Controller rayParams (line 191) runs `if session.Manifest.BuoyantProps then table.insert(exclusions, session.Manifest.BuoyantProps) end` and then sets `params.FilterDescendantsInstances = exclusions`. In Roblox that property is an array of Instances, and assigning an array that contains a non-Instance raises a cast error ('Unable to cast value to Objects').

The first call comes from `candidates()` → `clearLine()` at the start of `spawnModel` (line 405). That runs inside the xpcall in requestSpawn, so every pass fails with this error. The rollback sets SPAWN_RETRY, and after three failures the retry interval becomes 30 s, indefinitely. Once pump 2 runs, the second hostile never appears, and the only sign is a `[Level 2 Pool Slide]` warning every 10 s.

The Navigator path (line 433) survives because `addExclusion` checks `typeof(...) ~= "Instance"`. The controller's own rayParams has no such check. The live builder returns no BuoyantProps field (nil), and ANALYSIS 3.2 lists the field as read but never built. The fake engine does not type-check FilterDescendantsInstances, which is why the offline tests did not catch this.
- Fix: Delete `BuoyantProps={}` from the returned manifest (leave it nil, as the live World Builder does). If a field is wanted later, it must be a single Instance such as a Folder, never a table.

## 2. [major; verifiers: major,major; upheld 2/2] Every 34-wide tunnel has an uncollided 5-stud gap at each mouth; players can walk off the floor edge into the void
- `ServerScriptService/Level 2 Systems/Level 2 Kit World Builder.ModuleScript.lua:1050` (builder-contract)
- Detail: makeCorridor clones `Tunnel_<variant>_<len>` and adds no side collision of its own. In the export, all lateral walls ('Level 2 Corridor Haunch Wall ±1' and 'Level 2 Corridor Side ±1 1..3') are 2*body_end = L - 11.5 long. That means they stop 5.75 studs short of each mouth (modules_tunnel.py: COLLAR 1.75 + TRANSITION 4.0 are 'a shaped closed feature' authored as mesh only). The kit builder forces every MeshPart to CanCollide=CanQuery=false (cloneComponent line 134), so the collar and transition jambs exist only visually.

The tunnel floor (and the wet variants' water floor at -1.5) is 34 wide (x ±17), but the hall wall's door hole is only 30 wide (±15) and the wall slab is only 1.5 thick (±0.75 about the plane). So at both ends of every tunnel, on both sides, the vertical face x = ±17 is open over z ∈ [0.75, 5.75] from the floor up to the roof collider. There is no hall floor or terrain outside the tunnel footprint between halls.

A player leaving a doorway at an angle steps off the 0.45-high side ledge onto the strip at x 15.4–17 and then into the void. They fall to FallenPartsDestroyHeight and die. This applies to Wet, Drain, Kids, Dry and Stair tunnels, about 55 tunnels × 4 holes per round. Narrow passages are not affected, because their walls run the full length.

KIT_SPEC 3 rule 2 says that where a shaped feature must block movement it gets a simple box Part. The tunnel collar is that case and has no box. The offline harness checks markers and lamp positions but never checks lateral containment at the mouths.
- Fix: Add four invisible box colliders per tunnel: CanCollide and CanQuery true, Transparency 1, no Level2_EntityGround. Each covers the mouth strip outside the 30x30 clear opening: local x = ±16 (2 wide, spanning 15..17), z = ±(L/2 - 2.875) (5.75 long), y from -3 to the roof collider bottom (32 + rise). The cleanest place is modules_tunnel.py as `m.collider('Level 2 Corridor Mouth Jamb ...')`; alternatively add them in makeCorridor after cloneComponent. Keeping them at |x| ≥ 15 leaves the 30x30 doorway and the Pool Slide corridor-fit envelope unchanged.

## 3. [major; verifiers: major,major; upheld 2/2] Pool Slide freezes permanently in tunnel stretches that findHall maps to a small room
- `ServerScriptService/Level 2 Systems/Level 2 Pool Slide Navigator.ModuleScript.lua:202` (layout-nav)
- Detail: findHall only matches a point by rectangle when the point is inside a hall. Every point inside a tunnel is outside all halls, so it falls back to the nearest hall centre. Kit layouts add Role="Small" rooms as halls. Their centres sit 24-40 studs from their walls, while big-hall centres sit 48-136 studs from theirs, so a small room beside a tunnel often wins. Small rooms connect only through Width-12 corridors, and the Pool Slide BFS skips those (corridorFits). In kit layouts the new _goalReachable therefore runs graphRoute from that small room and gets nil.

The controller calls SetGoal every 0.15 s (GOAL_REFRESH_SECONDS). On a nil route SetGoal calls Stop() and returns false. The watchdog's SetGraphGoal(…, true) does the same. Stop() clears Goal, so Step never re-requests a path. Once the rig's foot enters such a stretch it stands still for good, unless a target comes into attack reach or also resolves to that same small room. The same mapping also makes a player standing in that stretch impossible to target.

Evidence: I replayed findHall over layouts written by the current generator. tuned/layout_203343134.json was written 3 minutes after the generator's last edit. In it, 25% of the floor of PressureDoor corridor 34 resolves to small room 45, and 7% of Open corridor 3. tuned/layout_618536553.json corridor 21 is also affected. In the older layouts, layout_733106 corridors 31/32 and layout_837834 corridor 8 (22 of 41 centreline samples) are affected. This is pure Lua logic, not a Roblox API question. test_level2_kit_navigation only uses hall-centre positions with every pressure door open, so it cannot catch this. The Pool Foam Navigator (line 197) has the same fallback. There it only gives the foam's graph fallback a wrong first hub (a small-room centre behind a wall), which is a minor effect.
- Fix: In findHall's nearest-centre fallback, skip small rooms. Containment still returns them: `if hall.Role ~= "Small" and distance < nearestDistance then nearest, nearestDistance = hall, distance end`. Live layouts have no Small halls, so live behaviour stays identical. Apply the same one-line change at Pool Foam Navigator line 197. Add an offline case that calls SetGoal from points inside each tunnel with the pressure doors closed.

## 4. [major; verifiers: major,major; upheld 2/2] Generator accepts big halls that are only tunnel-reachable through the locked grand hall
- `ServerScriptService/Level 2 Systems/Level 2 Kit Layout Generator.ModuleScript.lua:975` (layout-nav)
- Detail: Two connectivity checks exist, and neither tests the state the Pool Slide actually plans in for the whole round.
- validateKit's 'tunnel graph' BFS (line 975) blocks only Narrow corridors and leaves pressure doors open.
- generateAttempt's lock check (line 706) and validateLayout (line 1188) block only PressureDoor corridors and leave narrow passages open.

The Pool Slide skips Width<16 corridors, and corridorBlocked keeps pressure doors shut until Level2ExitPowered. So a big hall whose only tunnel goes to the grand hall passes both checks but cannot be reached by the Pool Slide. tuned/layout_618536553.json (current generator) has this: hall 9 (Entity Den B) has exactly three corridors: PressureDoor 8 to grand hall 15, plus Narrow 52 and Narrow 53 to small rooms 7 and 8.

For the whole pre-exit round:
- players in that hall cannot be reached;
- its den/patrol anchors are rejected at spawn;
- the Pool Slide freezes whenever it targets someone there.

This breaks KIT_SPEC §6: 'The big halls must be fully connected by tunnels alone.'
- Fix: In validateKit, before line 975 add `for i, c in ipairs(layout.Corridors) do if c.Kind == "PressureDoor" then blocked[i] = true end end`. Change line 977 to `if hall.Role ~= "Small" and hall ~= layout.GrandSlideHall and bigDistances[hall.Index] == nil then`. The grand hall's own tunnel access is already guaranteed: line 699 rejects narrow passages into it, and its PressureDoor tunnels join big halls only. The rejected plans just retry under the existing attempt budget.

## 5. [major; verifiers: major,major; upheld 2/2] Pool Slide targets the nearest player even when unreachable, and now stands still
- `ServerScriptService/Level 2 Systems/Level 2 Pool Slide Controller.ModuleScript.lua:578` (layout-nav)
- Detail: chooseTarget picks the nearest living record by 3D distance. It keeps the current target sticky within +15 studs and never checks reachability. In live layouts every player is reachable, so this never mattered. In kit layouts the new navigator gate makes SetGoal and SetGraphGoal call Stop() and return false for any goal reached only through Width-12 passages.

So whenever the nearest player stands in a small room or a narrow passage (the intended escape route), or in a big hall like the one in finding 2, the Pool Slide idles in place. It does this every 0.25 s target refresh, for as long as that player stays there, and ignores reachable players who are slightly further away. One hiding player turns the hostile off for the whole party. The offline navigation test checks only that SetGoal rejects such goals, not what the controller does next.
- Fix: In chooseTarget's loop, skip records the navigator cannot reach: `if session.Navigator:_goalReachable(record.Root.Position) then (existing nearest test) end`. Apply the same check to the sticky `current` before returning it. On live layouts _goalReachable always returns true (no Width<16 corridors), so live targeting is unchanged. The cost is one BFS over about 50 halls per living player every 0.25 s.

## 6. [major; verifiers: major,major; upheld 2/2] Helix Core and Spiral Core colliders are built as short horizontal drums instead of vertical columns
- `tools/level2_blender/import_kit.py:469` (importer)
- Detail: In Roblox, a Part with Shape = Cylinder always lies along its local X axis. Its length is Size.X and its diameter is the smaller of Size.Y and Size.Z. The importer only turns a cylinder upright when the record carries NativeRotationZ, and validate_export (lines 176-178) never requires that attribute. Four colliders in the real export have no Native* attributes: 'L2K Helix Core' and 'L2K Spiral Core' in SlideHall and in GrandSlideHall. They come from slides.py:541 and slides.py:594 and have sizes like (9, 76, 9) and (8, 55.45, 8). Because nothing rotates them, each becomes a cylinder about 9 studs long lying on its side at mid-height (y 38 for the SlideHall helix, about 26.9 for the spiral). The visual core MeshParts are CanCollide = false, so at floor level players walk straight through the helix and spiral columns. On the spiral stair the centre shaft (radius under 3.3) is open from top to bottom, and an invisible drum hangs among the treads. Pool Foam's GetPartBoundsInBox checks see the full 9x76x9 box, so the AI avoids a column that players pass through. The import test's fake checks cylinders only through Native* attributes, and its fixture does not include these four records. I confirmed this against the real export by running --plan into G:/Roblox/_local/l2blender/review_staging_cr_20261003.
- Fix: At slides.py:541 and :594, emit the same metadata modules_arch.py:195-196 uses: attrs={'CylinderAxis':'Y','NativeSizeX':h,'NativeSizeY':d,'NativeSizeZ':d,'NativeRotationZ':90}. In validate_export, reject any Cylinder collider that has no NativeRotationZ unless size[1] == size[2], meaning it is already X-native.

## 7. [major; verifiers: major,major; upheld 2/2] Tunnel mouths have no side collision for 5.75 studs at each end; players can walk through the collar and fall out of the map
- `G:/Roblox/MongoTV/tools/level2_blender/modules_tunnel.py:240` (kit-geometry)
- Detail: In `tunnel_shell`, the six side colliders (238-240) and both haunch-wall Parts (209-211) are only `2*body_end = length - 2*(COLLAR+TRANSITION)` long. The export confirms it: `Tunnel_Wet_64` has side colliders 52.5 long, which leaves z 26.25..32 open at each end. The comment at 232 ('No boxes enter either clear mouth or its rectangular collar') makes this deliberate, but nothing else seals the gap. The collar/transition loft is a Tile MeshPart with CanCollide false, and DoorArch30 is mesh-only with no colliders. The hall wall slab is 1.5 thick, centred on the hall edge, so it only covers z ±0.75 around the tunnel end. Result: inside the last ~5 studs of every tunnel nothing blocks sideways movement past the ±12.1 rib line. The floor parts (Water Floor, Dry floor) run out to ±17 and there is nothing beyond. A player hugging the visible collar walks through it and falls into the void between halls; the Round Adapter only fills Air there, so they fall to FallenPartsDestroyHeight. Live Level 2 does not have this hole: read-wb-tunnels.md section 7 describes full-length `Corridor Wall` backstops (inner face ±15.25, length G+3.26). This is a regression against the ANALYSIS 3.5 envelope.
- Fix: Add one full-length invisible backstop per side in `tunnel_shell`, placed outside the 30-wide clear mouth and behind the ±12.1 rib line. For example, after `roof_bottom` is computed: `m.collider(f"Level 2 Corridor Shell Backstop {side:+}", (side*16.125, (roof_bottom-3)/2, 0), (1.75, roof_bottom+3, length))`. That gives an inner face at ±15.25, y from -3 to roof_bottom, and adds 2 instances per tunnel. Then re-export, re-run `import_kit --plan`, and add an offline assert that the side containment covers the full length.

## 8. [major; verifiers: major,major; upheld 2/2] Helix Core and Spiral Core collide only as small horizontal discs, so the columns have no collision at floor level
- `G:/Roblox/MongoTV/tools/level2_blender/slides.py:541` (kit-geometry)
- Detail: `slides.py:541` emits `L2K Spiral Core` with size (8, top-base, 8), and `slides.py:594` emits `L2K Helix Core` with size (9, h, 9). Both use shape='Cylinder' and empty attrs. Manifest records: SlideHall Helix Core [9,76,9], Spiral Core [8,55.45,8]; GrandSlideHall [9,96,9] and [8,75.45,8]. The importer (`import_kit.py:467-472`) only corrects a cylinder's axis when `attrs.NativeRotationZ` is present, the way `modules_arch.py:195-196` does for ColumnCollider. These four records skip that branch and become unrotated Cylinder Parts. In Roblox a Cylinder's length always runs along local X, with diameter min(Size.Y, Size.Z). So each 'column' collides as a 9×9 or 8×8 disc lying on its side at mid-height (y≈38 / 26.9 / 48 / 36.9). The visible 76/96-stud helix column and the spiral-stair core (non-colliding MeshParts) have no collision from the floor up: players and Pool Foam walk through them. Pool Foam sight and kill rays respect CanQuery and nothing queryable is left there, so the foam can see and kill through the columns. The Spiral Core disc also pokes about 0.7 studs into the inner ends of treads 25-27. The fake engine cannot catch this: `test_level2_kit_import.py:272` only models cylinders that carry the Native* attrs.
- Fix: Give both records the column convention, then re-export so slides.json `prefabColliders` still matches the manifest. Spiral: `attrs={'CylinderAxis':'Y','NativeSizeX':top-base,'NativeSizeY':8,'NativeSizeZ':8,'NativeRotationZ':90}`. Helix: `attrs={'CylinderAxis':'Y','NativeSizeX':h,'NativeSizeY':9,'NativeSizeZ':9,'NativeRotationZ':90}`. Alternatively, make the importer treat any Cylinder with no Native attrs whose Size.Y is its longest side as Y-axis: Size = (Y, X, Z), then rotate by CFrame.Angles(0,0,π/2).
