Desktop uses 64 px squares with 8 px gaps. Touch uses 56 px squares with 6 px gaps; 52 px is reserved for a safe height too short for the preferred stack plus margins. X is Safe.Left + 8. The complete stack is centred between Safe.Top and Safe.Bottom, with at most half a pixel of rounding. Desktop ignores phantom touch geometry. The same three-pixel image inset, fitted artwork, border, palette, caption height, and font rules apply to every square.

On the captured phone, the 180 px stack's ideal position is y65–245 in the 310 px safe height. The visible resting stick glyph occupies x29–103/y217–291. The smallest safe shift is 36 px upward: y29–209, leaving 8 px before that glyph. The code chooses the nearer feasible position above or below the measured glyph. If neither fits, the centred rail remains visible; it is not hidden or moved right. The broad invisible joystick activation region deliberately remains outside this exclusion. Native button taps and stick behavior must be checked together. Very short viewports that cannot contain even the 52 px stack do not have a guaranteed safe fit.

The old `ZyntraSideMuteSlot`, briefing measurement, and Store-specific briefing/joystick watchers are removed. Existing Store modal, briefing, round, DEV-chip, and UIDevice relayout mechanisms remain. The glyph is re-read on those existing layout passes; this code does not move the rail on each joystick motion event.

Integration seams are explicit. `SECTION_IMAGES.Music` contains the root-provided uploaded asset `rbxassetid://102262986416811`; no upload was performed by this preparation. Pauli composes only the existing Settings toggle/refresh block against `local musicButton`, named `ZyntraMusicButton`. Its caption lives at `SectionButtonContent.SectionCaption`, initially `music`; the agreed short labels are `mute` / `unmute`, with full button text `mute music` / `unmute music` hidden behind the artwork caption. The full words do not fit the narrow single-line caption. Before `LobbyMusicEnabled` is a boolean the button stays visible but inactive. Both boolean values are clickable; the existing Settings behavior allowing a second toggle during pending is preserved by Pauli's shared handler. Store owns the button's visibility and layout, not the music request.

Validation: 261 checks execute the actual builders/layout/visibility and the actual UIDevice `rememberedFlag`, `SetEnabled`, and `SetInteractive` functions in the existing controlled host. They cover equal dimensions/gaps/order, centre and safe-origin arithmetic, the native phone glyph, minimal displacement, explicit relayout, adaptive 52, unavoidable-glyph fallback, unknown/OFF/ON setting gates, modal and round recovery, and preserved DEV behavior. Three targeted negatives reject top alignment, enabling an unknown profile, and permanently caching a false selection capability. Both whole sources compile. This is prepared layout evidence; composed shared requests, native image loads, typography/interaction and publication require the composed candidate's acceptance.

The first review found that explicitly setting `musicButton.Selectable = false` before UIDevice's first pass would cache false permanently. That initializer is removed. The readiness gate disables selection only after UIDevice has remembered the default capability; later visibility and enabled passes can restore it. The earlier host assigned selection directly and missed this boundary, so the final host extracts the actual UIDevice functions and includes the specific failing initializer as a negative control.
