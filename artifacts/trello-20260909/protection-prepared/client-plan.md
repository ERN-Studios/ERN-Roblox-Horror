# Protection item client integration — preparation

No client runtime source has been edited. The server transaction is being prepared separately; the owner-approved price and duration are five tokens and five seconds.

Use the existing measured `makeProductCard` in ZyntraStore for one token-item card. Keep its normal product layout registration, text sizing, scrolling and 44px touch floor. A TokenItem kind must bypass both Marketplace product lookup and purchase prompts; its action is BuyProtection, with price text `5 TOKENS`, stored-charge count and a pending/disabled state. The item has a neutral text monogram, not an invented Marketplace image. Purchase adds a stored charge; it does not activate protection in the lobby.

A small client module for this one item will coordinate the card and the separate in-round use HUD. It owns one pending command across both views and listens to the existing private ZyntraProfileChanged payload. Requests use existing ZyntraAction, with exact `{SessionNonce, Revision}` and action BuyProtection or UseProtection. Retry preserves all three identity fields. It must not manufacture another command on timeout, revive an effect from a terminal response or accept stale initial profile loads over a newer revision. No additional remote, currency, inventory framework or client-authoritative protection is needed.

Server DTO currently provides ProtectionCharges, ProtectionRevision, ProtectionSessionNonce, ProtectionAvailable, ProtectionPending and ProtectionLastResult. Root identified a missing correlated refusal response: a generic notification cannot safely distinguish a definite noncommit from an unknown DataStore result. The transaction agent has been asked to provide an identity-matched Rejected/Reason response for definite refusals while preserving unknown requests for retry. Client implementation waits for this contract.

The HUD will show a stored-count use button and the server display deadline. It reads PlayerProtectionActive/PlayerProtectionExpiresAt and Workspace:GetServerTimeNow solely for rendering. A use command is available while alive in-round, including a cancellable capture, and is unavailable after death, escape or round teardown. Protection is not automatically used at round start. Keyboard Q and controller D-pad Down are the selected candidate bindings; pass input through during chat, focused text entry, Roblox menus, screen-owning modals or invalid contexts, and accept only one Begin event. The existing spectator Q binding is disjoint because dead players cannot activate this item.

Touch placement belongs in UIDevice's existing ControlPlan, not a new independently positioned overlay. Add one ProtectionUse slot above the second column, retaining all six existing slots. The shared short-landscape row algorithm already derives its count from CONTROL_KEYS_RIGHT_FIRST; verify seven controls in one row or four/three rather than duplicating layout arithmetic in the HUD. Register the actual button rectangle. The control remains at least44px and shares modal suppression with the cluster. Display order must leave it usable during the L1 capture cinematic without overriding real screen-owning dialogs. Native testing must cover short landscape, narrow portrait, tablet, desktop/controller and input-mode changes.

The initial implementation will remain in artifact proposals until the prior fixes are individually published. Final merge must use the latest Store/UIDevice baselines and the reviewed transaction contract. Required focused checks cover matching refusal/success/retry, stale profile ordering, held input and simultaneous card/HUD activation; native checks cover measured Shop layout, use/countdown and capture cancellation. This document is a preparation decision, not implemented or accepted UI.
