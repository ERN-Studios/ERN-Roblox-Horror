# Loading camera movement — prepared fix

Card [pzVtej6w](https://trello.com/c/pzVtej6w), read directly from Trello: “Sometimes after the player loads in, the game forces their camera to move upward. Remove this behavior so the camera is not automatically moved after loading has finished and remains under the player's control.” To Do/incomplete; no comments or checklists returned. Saved in `card-readback.json`.

## Diagnosis from current source

The concrete automatic entry camera writer is `scheduleElevatorShake` in the baseline RoundUI at lines 3855–3984. The `elevator` event calls it at line 4164 after the loading-cover release path. One second later it binds a callback at `Enum.RenderPriority.Camera.Value + 2`, after Roblox's normal camera update. Each frame it multiplies the current camera by translation and pitch/roll offsets. Its ten-second sway ends with a one-second stop whose pitch is explicitly positive: `sin(joltPhase * pi) * 0.28` degrees.

GameManager commits the shared entry barrier and sends `entryreleased` at line 1811. It then sends the real elevator events in the Level 1 path at line 2461 (configured duration, default 19 seconds) or the direct Level 3 service-elevator path at line 2448 (7 seconds). RoundUI's `entryreleased`/`elevator` branches uncover the view, then the delayed camera effect runs for another eleven seconds. The `start` branch only sets `shakeScheduled=false`; it does not invalidate or remove the existing callback. Consequently the 7-second Level 3 ride can end while this camera writer is still running in gameplay. Normal noise can also have positive pitch before the final stop.

This establishes a concrete matching source path; the exact reported player's session was not captured and source diagnosis is not a claim of native reproduction. An independent scan by `audio_readiness` found no other automatic entry pitch writer in the current client sources. Spectate rotates only while watching a dead/escaped player's target, Jumpscare requires an actual capture, EntityShake changes Humanoid.CameraOffset rather than camera rotation, the Level3 hiding camera preserves existing rotation, and the Foam camera nudge requires a live Level2 effect event. Those encounter and player-control paths remain untouched. Briefing/intro code does not rotate the view. The older graph query identified the function but had stale line numbers; all conclusions above use the current source.
