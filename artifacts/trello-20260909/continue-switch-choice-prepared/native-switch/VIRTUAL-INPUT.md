# Supported rapid input option

The official current API exposes `UserInputService:CreateVirtualInput()` and `VirtualInput:SendMouseButton` with **security None**. The factory may return nil; its documented purpose is testing a running experience's own UI. Mouse button input uses the engine's hardware input path; it rejects CoreGui overlap and duplicate down/up state. These are the public `VirtualInput` APIs, not internal `VirtualInputManager`.

Primary sources checked 2026-09-10: [UserInputService source reference](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/UserInputService.yaml), [VirtualInput source reference](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/VirtualInput.yaml), [Roblox's testing API announcement](https://devforum.roblox.com/t/new-studio-testing-apis-and-assistant-improvements/4657854). Older June forum reports about plugin-only access are not evidence against the current documented security contract. Actual availability in the separately launched client still needs root's check.

`virtual-three-clicks.client.luau` is an **input test fixture**, not read-only execution. No UI/source/settings operations have been performed while preparing it. Root may run it once in actual client A's Command Bar, before the next win, with `EXPECTED_USER_ID` matched to that real client. It arms for240s, waits for the real win packet and real visible/active buttons, then sends actual mouse move/down/up events at their freshly measured centers. The current RoundGui has IgnoreGuiInset=true. Native calibration showed that this does not make the measured GuiObject center a virtual-input screen point: the fixture uses the GUI center for hit testing and adds the current `GuiService:GetGuiInset()` top-left vector for virtual input. It then waits at most 0.75 seconds for the actual `GetMouseLocation()` to reach that screen point within 2 pixels. `MouseBehavior` is logged, not used as an acceptance gate: the modal result buttons can permit a free pointer while camera/UI render callbacks momentarily disagree on that enum. Current window, button, input ownership, geometry and hit test are checked again after yields and before down. No mouse-policy, OS-focus or property changes are made.

Clicks are scheduled no earlier than .5/1.5/2.5 seconds after receipt of the next actual win packet. Each step also waits for the same serial's **newer server `postwinchoices` revision** with that user's expected `continuing → returning → continuing` choice before sending the next. This must be an L1/L2 win: actual L3's missing NextLevel means Continue is hidden, so the fixture refuses it. It does not call a GuiButton signal, application callback, or FireServer. It logs each sent click separately from accepted packets. On unavailable input, UI obstruction, missing acceptance, replaced window or timeout it stops; no bypass or hidden fallback. It releases only a mouse-down it successfully sent and disconnects its listener. Explicit cancellation: `_G.ContinueSwitchVirtualInput.Stop("root cancelled")` when armed. Final compact report: `_G.ContinueSwitchVirtualInputReport`.

Keep the reviewed A/B/server observers running. A's local accepted packet is not enough to claim two-client display replication: B must receive the same serial/revisions and show A's choices; the server's final outcome and actual next-level readiness remain separate acceptance. Call the action **documented virtual mouse input in two real test clients**, not three physical mouse clicks or human testing.

Root must keep A's native test viewport rendering and inspect any API error; do not change engine/settings/security to force availability. If the child client returns nil or fails to dispatch after one properly targeted attempt, the honest fallback is a separate registered authoring-client three-click test plus separately recorded real two-client replication. Do not combine those into a claim that the full three-switch sequence was observed in the same two-client session.

Root reported a native client A Command Bar availability result at15:11:33.336: `SWITCH_VIRTUAL_INPUT_AVAIL true VirtualInput -1`. This verifies construction in that actual client; no dispatched/accepted input is yet claimed here.


## Native calibration and correction, 2026-09-10

Serial 4 sent an API click but produced no actual button Activated or accepted choice; its evidence remains in `virtual-attempt-1528`. The isolated calibration's actual client logs are saved in `native-input-calibration-events.json`: both repeatCount 0 and 1 produced actual Activated, so the default 0 is retained. That calibration also exposed the 58-pixel top inset and a locked-center cursor; it does not by itself prove that a move to an off-center result button works.

The inset-corrected serial 5 fixture (`virtual-three-clicks.before-frame-phase.luau`, SHA 0d7305c6558927535f6716ce8273307bf0664fe9a591043b7455ababf40cb892) stopped before any down because the transient MouseBehavior enum changed after RenderStepped. This is an input-fixture refusal, not a server-choice failure. The current correction removes that enum dependency and requires actual pointer arrival; it retains the same server-confirmed three-choice acceptance and cancellation ownership. A stationary locked-center pointer cannot pass for an off-center button. `frame-phase-correction.diff` preserves the narrow change.
