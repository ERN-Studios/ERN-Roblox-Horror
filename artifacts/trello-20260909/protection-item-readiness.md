# Five-second protection item — implementation readiness

Read-only plan for [ak8Mgaeq](https://trello.com/c/ak8Mgaeq), using current source on 9 September 2026. The original request is an item bought with tokens, used later, making the player invisible to entities and preventing death for five seconds. The owner's later clarification overrides the old unspecified-price sentence: **5 tokens per use, 5 seconds**. No code, Studio, UI, publish or Trello changes were made for this assessment.

## Minimal implementation

Add one item definition to `ReplicatedStorage/ZyntraConfig.ModuleScript.lua` with a stable key, price=5 and duration=5. Add an integer owned-charge field to the existing Zyntra profile, its normalizer and private profile payload. Reuse the existing DataStore/profile lock, `ZyntraAction` actions, `ZyntraProfileChanged`, store card sizing and notifications. This is an inventory purchase, not a new Roblox developer product/pass, so it needs no Marketplace asset, checkout prompt, Robux price or ProcessReceipt branch.

Add one small **server-only** module, for example `ServerScriptService/PlayerProtection.ModuleScript.lua`, with `Activate`, `IsActive(player, character)`, `Clear` and one activation notification used for cancelling existing attacks. Store `{character, roundEpoch, activationId, expiresAt}` privately. Every predicate checks the server's current time against the absolute deadline; a delayed cleanup callback never decides whether protection still exists. Publish only the display deadline/state for the client. Character identity and round epoch fence old callbacks. Do not introduce a generic effect framework, damage bus, inventory framework or per-frame DataStore writes.

Use one server-derived clock for the five-second promise and expose `expiresAt` for a client countdown using `Workspace:GetServerTimeNow`. Client time/state cannot authorize activation or extend the server deadline. Roblox documents the synchronized clock as a client approximation; gameplay timing remains on the server. [Official Workspace API](https://create.roblox.com/docs/reference/engine/classes/Workspace#GetServerTimeNow).

An ordinary ForceField cannot implement this item: four current lethal paths directly set Health=0. Roblox explicitly documents that direct Health assignment bypasses ForceField. Gate the real kill sites before health changes **and before fatal feedback/capture side effects**. Do not revive a Humanoid in HealthChanged after it has already died. [Official ForceField API](https://create.roblox.com/docs/reference/engine/classes/ForceField).

## Buy/use transaction and lifecycle

Reuse `ZyntraMonetization.mutate` at line622: its local lock serializes mutations, and the UpdateAsync callback sees current durable balance. Buy must atomically check Tokens≥5, subtract5, add exactly one charge and record the accepted operation identity. Normalize new counts to finite nonnegative integers; refuse when the profile is non-persistent/unavailable. Check obvious no-funds/invalid requests in memory before spending DataStore budget, and recheck inside the transform. Mark purchase as a write-bearing action in the existing per-action limiter. Rate limiting is not idempotency.

Use a small **per-item operation revision/result**, not an ever-growing receipt list. Bind requests to a server-issued session nonce and expected revision; accept only one outstanding request per player/item, repeat the same ID on uncertain results, and reject older revisions without reapplying a delta. Store the operation's identity/status with the charge mutation so a retry can recognize a committed request. UpdateAsync callbacks can rerun: no activation, remote, timers or other side effects inside them. Test contention against token gifts/upgrades and a second server's newer profile revision. Do not report a conflicted or ambiguous write as successful merely because the balance changed.

Use consumes a stored charge rather than charging five tokens again. Reserve/consume it through the same profile transaction with an operation ID and a small saved reservation status, then revalidate exact character, living Humanoid, active round, participant membership, not Escaped/not exit-transition, and the still-current operation **after every yield**. Only then start the full five seconds. Starting while already active refuses without spending, stacking or refreshing. A slow DataStore response must not use up the effect's displayed duration.

If the character dies, leaves or the round changes before activation, resolve the reservation with an **idempotent compensating update keyed to that reservation**, restoring at most one charge. Prevent a new use from replacing an unresolved reservation. The existing Emergency Re-entry path at1817 is useful for eligibility/revalidation structure, but its `+=1` retrying refund must not be copied as an exactly-once guarantee. Unknown commit outcomes require re-reading/retrying the same operation identity, not a new ID or blind refund. Keep cross-server/rejoin resolution fenced to the saved operation; an active effect is never restored on another character/server. This is the only persistence-specific complexity the item needs.

Activation during an attack is allowed while alive, including the L1 capture. Cancel the capture and pending attack, then allow the player to escape for the remaining absolute five seconds. If the fatal mutation won first and Health is already0, refuse/return the unused charge; this item is not resurrection. At expiry eligibility returns normally and a new valid attack can begin; cancelled attacks must never resume from a stale latch. Do not heal missing health, replenish stamina/battery or refresh another immunity timer.

Clear effect state and connections on character removal/death, PlayerRemoving, InRound=false, Escaped=true, exit transition and round end/change. A round epoch can be owned by the small service and advanced on authoritative round lifecycle changes; do not rely solely on SelectedLevel, since two consecutive rounds can use the same level. A cleanup timer checks activation ID so an old timer cannot erase a later purchase's effect. Existing hidden/flush immunity remains valid independently.

Reuse ZyntraStore's measured Shop product-card layout (`:1111–1190`) for “5 TOKENS / one use”, owned count and purchase-pending state. Correct the token-product descriptions that currently say every token buys a permanent upgrade (`ZyntraConfig:57,65`). Add one compact in-round use action/countdown, independent of the full terminal. `UIDevice.Layout`, `TopRightPanel`/`ObjectiveColumn`, `RegisterControlRect`, `Binding`/`Caption`, `SetEnabled` and modal guards already exist; reuse them rather than inventing new safe-area/control layout. A candidate unused binding is **Q / D-pad Down** while alive in-round, with one Begin event. Q is already spectator previous-target, so eligibility must make those contexts exclusive; D-padUp is objectives, LB/B dispatch, RB flashlight, X glowstick/hiding, Y reader and L2/L3 sprint/crouch. Return Pass in menu/chat/modal/text-entry/invalid contexts, and prevent a single press from both selecting UI and consuming. Permit the dedicated use control during a cancellable L1 capture even though movement is disabled; do not hide it behind the cinematic. Use >=44px touch target, avoid movement/objectives, and show owned/active/remaining/unavailable states without requiring a terminal visit during pursuit.
