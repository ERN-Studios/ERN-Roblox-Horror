# Verified audit — 2026-09-03

Thirty-six defects that survived adversarial review, and the five already shipped.

**How to read a finding.** Each was produced by a dimension sweep, then given to three
independent reviewers whose brief was to refute it: one checked every load-bearing fact,
one hunted for the guard the finder had missed, one asked whether it mattered at all.
`refuted 0/3` means all three tried and none could. `1/3` means one dissented — usually
the reviewer asking whether it was worth the time.

Sixty-nine candidates went in; thirty-three were refuted and dropped. Two of the drops are
worth knowing about because they look like obvious wins and are not: deleting the 100 MB
of split tar parts under `assets/source-packs` does **not** shrink the clone (the blobs
stay in history), and moving `Round Completion Test Suite` out of the ServerScriptService
root was judged not worth the churn.

**Before you start:** run `python tools/pull_source_from_studio.py --audit`. This place is
edited from other sessions and the line numbers below drift. Apply every change in Studio
first, then mirror to the repo — never the other way round. See CLAUDE.md.

`ServerScriptService/GameManager.Script.lua:2624` · severity **serious** · refuted 0/3

**Fix**

Kill the unbounded wait everywhere at once by having the helper return the character instead of a boolean — `nil` stays falsy, so the two call sites that already test the result (:1957, :2008) keep working unchanged.

Then at each of the three broken sites (:2623-2624, :1891-1892, :2285-2286) replace the pair with:

One player who fails to load is dropped from the round; the rest start. That matches what the Zyntra path at :2008 already does. `player.Character or player.CharacterAdded:Wait()` at :2013 can drop its `:Wait()` half the same way.

Consequence: for Levels 1 and 3 there is no client-side backstop at all (only Level 2's held cover has one, RoundUI.LocalScript.lua:4003), so "indefinitely behind the loading cover" is literally true there.

> **Reviewer correction.** Three small corrections, none of which change the verdict. (b) "no error, no warning" overstates it — `loadGameplayCharacter` does `warn("[GameManager] Gameplay character load failed:", err)` at line 427, so the log *does* show the cause; what is silent is the hang itself. ### pinnedSeedOverride's modulo maps the largest accepted seed back onto 0, the value the guard exists to reject — **SHIPPED**

`ServerScriptService/Level 2 Systems/Level 2 Round Adapter.ModuleScript.lua:38` · severity **minor** · refuted 0/3

**Fix**

Reject out-of-range instead of wrapping, in both adapters. The adapter's modulo buys nothing anyway — `LayoutGenerator.normalizeSeed` already applies `% MAX_SEED` downstream.

	return math.floor(requested) % MAX_SEED
becomes

	return math.floor(requested)

Worth a one-line doc touch: HANDOFF-LEVEL2.md:17 and README.md:344 should say the range is 1 .. 2147483646.

> **Reviewer correction.** The guard's original purpose — a zeroed/cleared attribute must not pin — is still intact; `0` takes the `requested < 1` branch and correctly yields a random seed. The state readback does report the aliased value (`Level2_Seed = 0`, `Level2_SeedPinned = true`), so it is discoverable rather than invisible. Impact is confined to developer reproduction runs — no shipped code path ever writes these attributes.

> **Reviewer correction.** Not "the guard is bypassed through the front door" — a pinned round is what the tester asked for, and they still get a deterministic, reproducible map. The accurate statement: the `% MAX_SEED` wrap makes the attribute silently build a *different* seed's map than the one requested at and above 2147483647 (2147483647 → 0, 2147483648 → 1, …), contradicting `README - LEVEL 2 TWEAKS.ModuleScript.lua:40` which documents "any number >= 1". On Level 2 the round genuinely builds seed 0's layout; on Level 3 it builds seed 1's, because `Level 3 Layout Generator.ModuleScript.lua:191` already remaps 0 → 1. No crash, no player-reachable path, no gameplay effect in a live round.
